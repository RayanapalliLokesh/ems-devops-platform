# State and the remote backend (Phase 20)

## What state is

`terraform.tfstate` is Terraform's memory: every resource it created, with its real ID (`vpc-...`, `i-...`,
`arn:...`) and last known attributes. `plan` compares **code** with **state**, refreshes state from **AWS**, and
proposes the difference. Lose the state and Terraform no longer knows it owns anything: the next apply tries to
create everything again (and fails on names that already exist). State can also hold secrets (user data, generated
values), so it is never committed (`.gitignore`: `*.tfstate`, `tfplan`, `backend.hcl`).

## Layout in this project

| Configuration | State | Lock |
|---|---|---|
| `terraform/bootstrap-state` | **local** `terraform/bootstrap-state/terraform.tfstate` (it creates the bucket the others use: chicken and egg) | none |
| `terraform/registry` | `s3://ems-tfstate-<account>/registry/terraform.tfstate` | DynamoDB `ems-tf-locks` |
| `terraform/envs/dev` | `s3://ems-tfstate-<account>/envs/dev/terraform.tfstate` | DynamoDB `ems-tf-locks` |
| `terraform/envs/prod` | `s3://ems-tfstate-<account>/envs/prod/terraform.tfstate` (planned only) | DynamoDB `ems-tf-locks` |
| `terraform/eks` | `s3://ems-tfstate-<account>/eks/terraform.tfstate` (not applied by default) | DynamoDB `ems-tf-locks` |

`bootstrap-state` creates:

- **S3 bucket `ems-tfstate-<account-id>`**: versioned (every state write is a new version, so a broken state can be
  rolled back), encrypted with SSE-S3 (AES256), public access fully blocked. The account ID in the name makes it
  globally unique without a random suffix, so the name is predictable for every other configuration.
- **DynamoDB table `ems-tf-locks`** (`LockID` string key, on-demand billing): while a `plan`/`apply` runs, Terraform
  writes a lock item; a second run (a teammate, the CD pipeline, `aws-playground.sh drift`) waits or fails instead of
  writing the state at the same time and corrupting it.

## Partial backend configuration: `backend.hcl`

Each configuration declares only the part of the backend that is specific to it:

```hcl
terraform {
  backend "s3" {
    key = "envs/dev/terraform.tfstate"
  }
}
```

The account-specific part is generated by `bootstrap-state` (`terraform output -raw backend_config`) into
`terraform/backend.hcl` (gitignored) and passed at init time:

```hcl
bucket         = "ems-tfstate-123456789012"
region         = "us-east-1"
dynamodb_table = "ems-tf-locks"
encrypt        = true
```

```bash
terraform -chdir=terraform/envs/dev init -reconfigure -backend-config=../../backend.hcl
```

Why partial: backend blocks cannot use variables, and the playground account changes with every session. The code
stays account-free; `-reconfigure` points it at the new account's bucket. CI runs `init -backend=false` (validate and
test need no state and no credentials).

## Order

```
bootstrap-state  ->  registry  ->  envs/dev   (-> eks)          create
envs/dev (eks)   ->  registry  ->  bootstrap-state               destroy (the state bucket goes last)
```

`scripts/aws/aws-playground.sh bootstrap | registry | up | down` runs exactly this order.

## Rules

- Never edit state by hand. Inspect with `terraform state list` / `terraform state show ADDR`; refactor with
  `moved` blocks; adopt existing resources with `import` blocks reviewed in a plan.
- Never run two applies at once; if a crash leaves a lock behind, check that nothing is running, then
  `terraform force-unlock <LOCK_ID>`.
- A broken state write can be undone from the bucket's object versions (download the previous version of the key,
  `terraform state push` it) - the reason versioning is on.
- `dynamodb_table` is deprecated from Terraform 1.10 in favour of S3-native locking (`use_lockfile = true`); see
  [playground-quirks.md](playground-quirks.md).
